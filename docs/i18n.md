# Internationalisation (i18n)

SCI Healthcare supports multiple languages across West and East African corridors:
- **English (`en`)** (default)
- **French (`fr`)** (West Africa)
- **Swahili / Kiswahili (`sw`)** (East Africa)
- **Yoruba / Yorùbá (`yo`)** (West Africa)

---

## Architecture

- **Message Catalogues:** JSON files located in `src/messages/` (`en.json`, `fr.json`, `sw.json`, `yo.json`). `src/i18n/messages.test.ts` fails CI when a catalogue is missing an English key, ships an empty string or drops a `{placeholder}`.
- **Configuration:** `src/i18n/config.ts` lists supported locales, display labels, date/number locales, and imports the JSON catalogues.
- **Provider & Hook:** `src/i18n/LocaleContext.tsx` provides `LocaleProvider` and the `useLocaleContext()` hook:
  - `t(key, params?)`: Translates dot-delimited message paths (e.g. `t('voucher.history')` or `t('voucher.scanToView', { id: '42' })`).
  - `locale`: Current active locale (`en`, `fr`, `sw`, or `yo`).
  - `setLocale(locale)`: Persists user preference to `localStorage` (`sci-locale`) and a `NEXT_LOCALE` cookie.
- **Persistence and first visit (#277):** the locale is a small store read through `useSyncExternalStore` — the same shape as the theme in `src/lib/theme.ts`. The root layout resolves it on the server from the `NEXT_LOCALE` cookie, then from the request's `Accept-Language`, and passes it to `LocaleProvider` as the server/hydration snapshot. The server HTML therefore carries the right `lang` and `dir` before first paint, and a French browser gets French without a flash of English. On the client the same order applies: `localStorage` (`sci-locale`), the `NEXT_LOCALE` cookie, `navigator.languages`, then English. An explicit choice always wins. `tests/e2e/language.spec.ts` pins the stored choice across navigations and reloads, plus detection with `locale: 'fr-FR'`.
- **Plural forms (#278):** a catalogue value may be an object keyed by CLDR plural category (`one`, `other`, and `zero`/`two`/`few`/`many` where the language uses them). `translate()` selects the form with `Intl.PluralRules` whenever `params.count` is a number, falling back to `other`. Adding Arabic or another language needs only its catalogue: the six categories and their rules come from the platform, not from app code.
- **Formatters:**
  - `formatDate(iso, locale)` in `src/lib/amounts.ts` formats dates per locale (`en-GB`, `fr-FR`, `sw-KE`, `yo-NG`).
  - `formatUsdc(amount, locale)` in `src/lib/amounts.ts` formats currency amounts per locale.
  - `timeUntil(iso, now, locale)` and `timeSince(iso, now, locale)` in `src/lib/amounts.ts` use `Intl.RelativeTimeFormat`, so durations read "in 3 days" or "il y a 3 jours" in the active locale instead of a concatenated suffix.
- **Contract & Protocol Errors:**
  - `src/lib/errors.ts` provides localized dictionaries (`VOUCHER_ERRORS_I18N`, `REGISTRY_ERRORS_I18N`, `FAUCET_ERRORS_I18N`) for host contract and token errors.
  - `src/lib/disputes.ts` provides localized dispute reason descriptions.

## How to Add a New Language

To add another language (for example, Portuguese `pt`):

1. **Create Message Catalogue:**
   Add `src/messages/<locale>.json` modeled after `src/messages/en.json`.

2. **Register in `src/i18n/config.ts`:**
   - Import the catalogue: `import <locale> from '@/messages/<locale>.json';`
   - Add the code to `locales`: `export const locales = ['en', 'fr', 'sw', '<locale>'] as const;`
   - Add to `messages`, `localeLabels`, `localeNumberFormats`, and `localeDateFormats`.

3. **Add Error & Dispute Translations:**
   - In `src/lib/errors.ts`, add entries for `<locale>` to `VOUCHER_ERRORS_I18N`, `REGISTRY_ERRORS_I18N`, and `FAUCET_ERRORS_I18N`.
   - In `src/lib/disputes.ts`, add entries for `<locale>` to `DISPUTE_REASONS_I18N`.

4. **Verify:**
   - Run `npm run typecheck`
   - Run `npm run test:unit`

## Right-to-left layouts (#131)

The layout is direction-agnostic, so a right-to-left language needs a
catalogue, not a second set of styles.

- **Direction comes from the locale.** `src/i18n/direction.ts` maps the
  language subtag to `ltr`/`rtl` (`directionForLocale`), and
  `LocaleProvider` writes the result to `dir` on `<html>` beside `lang`.
  The server renders `dir="ltr"` because it renders English; the stored
  locale is applied after hydration, exactly like the language itself.
- **Components use logical utilities only.** `ms-`/`me-`, `ps-`/`pe-`,
  `text-start`/`text-end`, `border-s-`/`border-e-`, `start-`/`end-` resolve
  against the `dir` attribute of the document, so nothing is positioned by
  screen left or right. A physical `ml-4` in a new component is a bug: it
  will sit on the wrong side once an RTL locale ships.
- **Two exceptions live in `src/app/globals.css`.** `.mono` is
  bidi-isolated, because an address or hash is a left-to-right run even on
  an RTL page; `.rtl-flip` mirrors a glyph that encodes direction, such as
  the demo tour's arrow — apply it per icon, never to a container.
- **Testing.** `tests/e2e/rtl-layout.spec.ts` sets `dir="rtl"` by hand (the
  acceptance criterion for #131) and asserts that the header cluster, the
  table alignment and the accent stripes follow it, at desktop and 390px
  widths. Do the same when reviewing a layout change: flip the attribute in
  the devtools and check the page, since no RTL catalogue ships yet.

To add Arabic, create `src/messages/ar.json`, register `ar` in
`src/i18n/config.ts` as described above, and the direction follows — no
component has to change.

## Translator's guide (no code required)

This section is for translators. You need a text editor and a GitHub account;
you do not need to run the app to translate, and you do not need to understand
the code. The developers' instructions are above.

### Where the text lives

Each language is one file: `src/messages/en.json` (English, the source),
`src/messages/fr.json` (French), `src/messages/sw.json` (Swahili) and
`src/messages/yo.json` (Yoruba). The files
have the same shape, so a key in one has a matching key in the others:

```json
{
  "voucher": {
    "voucherNumber": "Voucher #{id}",
    "scanToView": "Scan to view voucher #{id}"
  }
}
```

Translate the text to the right of the `:`, never the key on the left (the part
before the `:`) and never the file structure. Do not delete keys, do not add
keys, and do not change the order — a missing key falls back to English at
runtime, and CI's `npm run test:unit` fails when a catalogue is missing an
English key or a placeholder.

### Placeholders

Anything in braces is a placeholder the app fills in at run time:

| Placeholder | What it becomes |
| --- | --- |
| `{id}` | A voucher number |
| `{code}` | A contract error code |
| `{count}`, `{shown}`, `{total}` | Numbers of items |
| `{net}` | A network name (Testnet, Mainnet) |
| `{done}` | A count of completed steps |

Copy them exactly, braces included, and keep each one in the sentence where it
reads naturally. `{id}` may move; it may not be renamed, translated
(`{identifiant}` breaks), doubled or dropped. If a sentence needs a placeholder
that English does not have, say so on the issue instead of adding one.

### Style

- Keep the tone of the English: plain, specific, no marketing. Explain the
  mechanism rather than reassuring ("Dispute window closes in 3h — settles
  after that", not "Processing").
- Match the register of existing entries in your language file rather than
  translating word for word. Shorter is better: buttons and table headers have
  very little room, and the mobile layout is 390px wide.
- Keep sentence case for labels (`My vouchers`, not `My Vouchers`), and keep
  the trailing punctuation of the English string.
- Leave brand names, `USDC`, `Stellar`, `Soroban` and addresses untranslated.
- `…` (a single ellipsis character) is used in progress labels; keep it.

### Preview it

```bash
npm install
npm run dev          # http://localhost:3000
```

Switch language from the picker in the header, then walk the pages the strings
belong to: home, a clinic page, `My vouchers`, `Clinic desk`, `Attest`. English
is the fallback, so a string you have not translated yet appears in English
rather than blank.

Two checks worth running before you submit:

```bash
npm run test:unit    # catalogues must have the same keys
npm run typecheck
```

### Submit it

1. Edit only `src/messages/<locale>.json` (and, for a **new** language, the
   files listed above under "How to Add a New Language" — ask on the issue
   first, a new language needs a maintainer to agree the locale code).
2. Commit with `docs(i18n): translate <area> into <language>` or
   `feat(i18n): add <language>`, and open a pull request from your fork.
3. Say in the pull request which pages you checked and whether you are a
   native speaker or working from the glossary. A reviewer who speaks the
   language will confirm before merge; untranslated or machine-only text is
   not merged.

### Adding a brand-new language file

A language file alone is enough to see it in the picker only after it is
registered — that part is code, in `src/i18n/config.ts`, and is described in
"How to Add a New Language" above. If you are not comfortable editing it, add
the file, open the pull request, and say which locale code and label you want;
a maintainer will wire it up.
